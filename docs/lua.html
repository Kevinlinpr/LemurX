Overview

LemurX is Chromium for Android with a Lua 5.4 interpreter living inside the browser process, on its own sequenced thread. Scripts are plain .lua files in the app's private directory. There is no manifest, no permission prompt and no extension API standing between the script and the browser: a script talks to tabs, the network stack, the native Android UI, the DevTools Protocol and Chromium's own services through one table, lemurx.

Three layers are available, and they compose:

lemurx.*The native LemurX API. Tabs, network rules, HTTP, files, storage, the browser shell, declarative native UI, native-view surgery, input, intents, cookies, history, prefs, the Chrome DevTools Protocol. browser process
luakit layerluakit's entire C-level Lua surface, re-implemented on Chromium: widget{} trees mapped to Android views, webview bound to a tab, luakit.register_scheme, sqlite3, regex, soup, stylesheet, timer, download, ipc_channel. luakit's lib/, lousy/ and rc.lua ship as-is and run. luakit
rendererA Lua state in every renderer process (luakit's web extension model): page, dom_document, dom_element over main-world V8 handles, the synchronous send-request hook on every subresource, luakit.register_function to expose Lua to page JavaScript, ipc_channel back to the browser process. renderer process

How to read the badges used throughout this page:

browser runs in the browser process · renderer runs in a renderer process · luakit luakit-compatible API · UGC ok allowed in sandboxed shared scripts · local only refused (Lua error) in UGC scripts · signal an event you subscribe to with add_signal.

Which layer should I use? Reach for lemurx.* first — it is the smallest, most Android-shaped API. Use the luakit layer when you want luakit's object model (signals, property:: notifications), its widget tree, custom URL schemes, or when porting luakit modules. Use the renderer layer when a decision has to be made synchronously inside the page: per-request rewriting, DOM surgery before first paint, exposing native functions to page scripts.

Conventions & trust domains

Threading

All scripts run on one sequenced Lua thread in the browser process. Most lemurx.* calls are synchronous: a call that needs the UI thread posts there and waits. Callbacks (events, clicks, timers, HTTP results) are delivered on the Lua thread, so there is no concurrency to reason about. The UI thread never blocks on Lua: a Java callback that needs a return value while Lua is busy is refused rather than waited for. The single exception is the luakit widget key-press verdict, which the UI thread awaits while cooperatively draining widget operations Lua enqueues.

  • Don't spin (while os.time() < t). Use lemurx.timer.after / every.
  • A synchronous lemurx.http.fetch blocks the Lua thread up to 20 s (UGC) / 120 s (local) — every script's callbacks queue behind it. Use the callback form or lemurx.async.
  • tabs.eval, cdp.send, ui.* are synchronous and fast (they wait on the UI or renderer, tens of milliseconds).

Return values

  • Queries return a table: {ok=true, ...} or {ok=false, error="why"}.
  • Actions return a boolean.
  • "Not found" is nil, not an error.
  • Type errors and privileged calls from UGC raise. Wrap with pcall when in doubt.

Local vs UGC

Scripts on your own device are unrestricted. Restrictions apply only to scripts other people wrote that you installed (UGC, files/lua/ugc/).

UGC scripts may not use: lemurx.cookie history downloads perm cdp v8 dom ax blink prefs data page network emulation overlay css, net.addRule's requestBody/replaceRequestBody, arbitrary intent actions, or the luakit layer. Privilege is checked at runtime by state, not by scanning source — dynamic code in UGC is still UGC.

Why a separate state? With a shared state a UGC file could overwrite lemurx.tabs.eval and run under your privileges the next time one of your callbacks called it (confused deputy). Separate states remove the class of attack, so local scripts need no defensive coding at all. Why text-only load? The Lua VM does not verify bytecode; crafted bytecode is arbitrary memory access in the browser process.

Local scripts hand capabilities to UGC explicitly with lemurx.expose; UGC picks them up with lemurx.import. Values cross as JSON; functions never cross.

Events

Two event styles coexist. lemurx.* uses module.on(name, fn); the luakit layer uses the object protocol obj:add_signal(name, fn) (see Object protocol). Both deliver on the Lua thread.

lemurx.* events
-- Tab lifecycle. ev = {id, url, title, incognito, loading, canGoBack, canGoForward, muted, event, eventUrl}
lemurx.tabs.on("started" | "document" | "loaded" | "created" | "closed" | "selected", function(ev) end)
--  started  = navigation begins       document = DOM available (best moment to inject)
--  loaded   = load finished           created / closed / selected = tab strip changes

-- Shell events
lemurx.chrome.on("omnibox", function(ev) end)   -- {focus=true|false, text}
lemurx.chrome.on("back",    function(ev) end)   -- {id, url, title}
lemurx.chrome.on("menu",    function(ev) end)   -- {id, title, lua}

-- Back key. Once registered the key is yours; call lemurx.chrome.back() to let it through.
lemurx.input.onBack(function(ev) end)
lemurx.input.interceptBack(false)               -- hand it back to the system

-- DevTools events (local only)
lemurx.cdp.on("Network.responseReceived" | "*", function(ev) end)  -- {method, tab, params}

-- Timers (ms, min 10)
local id = lemurx.timer.every(60000, function() end)
lemurx.timer.after(2000, function() end)
lemurx.timer.cancel(id)
luakit-style signals
local webview = require("webview")
webview.add_signal("init", function(view)                 -- every webview, native tabs included
    view:add_signal("navigation-request", function(v, uri, reason)
        if uri:find("ads%.example") then return false end -- veto: the navigation never happens
    end)
    view:add_signal("property::title", function(v) msg.info("title now %s", v.title) end)
end)

luakit compatibility

luakit is the WebKitGTK browser whose entire UI is Lua. LemurX re-implements every C-level interface luakit exposes to Lua — the globals, the object protocol, all widget types, the webview, custom schemes, the web-extension (renderer) side — on top of Chromium and Android. luakit's own pure-Lua layer (lib/, lib/lousy/, config/rc.lua, config/theme.lua) is shipped byte-for-byte and required normally. That means require("webview"), require("window"), chrome.add(...), modes, binds, adblock, follow, formfiller, userscripts… all work.

Enabling the luakit shell

The kernel always loads (so widget{}, sqlite3{}, luakit.register_scheme are available to your scripts). Whether rc.lua runs — which hands the whole shell to luakit's window.lua: notebook, tab strip, status bar, vi-style modes — is a switch:

toggle rc.lua
lemurx.storage.set("luakit_rc", "1")        -- run config/rc.lua at startup (luakit shell)
lemurx.storage.set("luakit_autowrap", "1")  -- wrap every native tab as a luakit webview (default on)
-- edit files/luakit/config/rc.lua and theme.lua like you would on the desktop

Deliberate differences

  • Pixels are dp, font sizes are sp. Pango font strings ("monospace bold 12") and Pango markup in labels are translated.
  • Webview is a tab. widget{type="webview"} creates a real Chromium tab; putting it in a notebook/box moves the tab's content into the widget's rectangle. notebook:switch() selects the native tab and vice versa.
  • navigation-request is a NavigationThrottle. Returning false cancels before commit; no flash, no history entry.
  • Custom schemes serve navigations and subresources; a request nobody finishes times out after 30 s instead of hanging forever; a scheme with no handler at all returns 404 immediately.
  • regex is RE2, not PCRE: no back-references or look-behind.
  • luakit.spawn runs a real process (/system/bin/sh is available); unique.is_running() is always false (one process per package).
  • Web modules cannot touch the file system (Chromium's renderer sandbox): lfs in the renderer is a consistent empty implementation.
  • Lua is 5.4; a compatibility shim provides unpack, loadstring, setfenv/getfenv, table.getn/maxn, math.pow, string.gfind, package.loaders for luakit's 5.1-era lib/.
Licensing. luakit's lib/ and lousy/ are GPLv3 and ship as separate Lua files with their license. LemurX's kernel (kernel/*.lua, the C++ and Java hosts) is an independent implementation written from luakit's documentation and is not derived from luakit's C sources.

Lua in the renderer

Every renderer process hosts its own Lua state, the equivalent of luakit's web extension. It is loaded with require_web_module("name") from the browser side; the module source is resolved from files/luakit/config/ then files/luakit/lib/ and pushed over Mojo. Inside, a module sees luakit, page, dom_document, dom_element, ipc_channel, msg, soup and the safe standard library.

What makes this different from a content script:

  • Real DOM handles, main world. dom_element wraps a V8 node handle. The same node is always the same Lua object (usable as a table key, comparable with ==). Reads and writes are synchronous.
  • Not a script tag. Page CSP does not apply; the page cannot see or interfere with the Lua state.
  • Synchronous request hook. page's send-request signal fires for every subresource before it leaves the process — return a string to redirect, false to block, edit the headers table in place. Backed by a URLLoaderThrottle.
  • Native functions on window. luakit.register_function(uri_pattern, name, fn) makes window[name](...) return a Promise resolved from Lua.
  • Two-way IPC. ipc_channel signals in both directions, with targeting to a single page or broadcast to every renderer.
files/luakit/config/probe_wm.lua (renderer side)
local ui = ipc_channel("probe_wm")

luakit.add_signal("page-created", function(page)
    page:add_signal("send-request", function(p, uri, headers)
        if uri:find("doubleclick%.net") then return false end        -- block
        headers["DNT"] = "1"                                            -- edit headers
        if uri:sub(1, 7) == "http://" then return "https://" .. uri:sub(8) end  -- redirect
    end)
    page:add_signal("document-loaded", function(p)
        for _, a in ipairs(p.document.body:query("a[target=_blank]")) do a.attr.target = "_self" end
        ui:emit_signal("links_fixed", p.id, #p.document.body:query("a"))
    end)
end)

luakit.register_function("^https?://", "lemurPing", function(page, resolve, reject, msg)
    resolve("pong: " .. tostring(msg))    -- page JS: await lemurPing("hi")
end)
files/lua/20_probe.lua (browser side)
local wm = require_web_module("probe_wm")
wm:add_signal("links_fixed", function(_, page_id, n)
    lemurx.toast(("tab %d: %d links"):format(page_id, n))
end)
wm:emit_signal("rules", { block = {} })              -- broadcast to every renderer
wm:emit_signal(view, "rules", { block = {} })        -- or only the renderer hosting this webview

Pitfalls & limits

  • net.addRule and subresources. Browser-side rules apply to navigations (document / sub_frame) and browser-initiated requests. For per-request control of page subresources use the renderer's send-request signal, which sees every img/script/xhr/fetch.
  • tabs.hide on the current tab blanks the screen — select another tab first.
  • theme.set({dark=...}) goes through LemurX's dark-mode switch and marks the app for restart; avoid toggling it often.
  • toolbar.* slots are 150 dp wide — one button, maybe two.
  • page.top / page.bottom are PopupWindows and are rebuilt on rotation; ui.update is much cheaper than re-render.
  • UI calls block. Don't ui.find forty times in one callback — dump once and filter in Lua.
  • eval returns JSON-serialisable values only. DOM nodes come back as nil; use the renderer layer if you need nodes.
  • Load order is file-name order. Cross-script globals need matching number prefixes; better, put shared code in files/lua/lib/ and require it.
  • Local scripts have all of os and io. os.exit() kills the browser process; io.open can read and write anything in the app's private directory. That is the point — don't teach it to beginners.
  • UGC scripts are isolated from each other too. Communicate through lemurx.storage or a local bridge script.
  • The bridge moves data, not functions. An imported function cannot take a Lua callback; poll storage or subscribe to events instead.
  • luakit init timing. webview.add_signal("init") only fires for webviews created after registration. For tabs that already exist, walk lemurx.tabs.list() and call __lk.webview_for_tab(id[, true]) (LemurX helper) to hook or wrap them, as the showcase scripts do.
  • A scheme request must be answered. If a handler is attached but never calls request:finish, the navigation fails after 30 s.

Publishing UGC scripts

  1. Place the file in files/lua/ugc/. Privilege drop and state isolation are automatic; you don't detect anything yourself.
  2. lemurx.ugc.scan(source) must return an empty table before listing. load(string) works (text only); dofile/loadfile/require/io/os do not exist.
  3. Anything that waits for the network uses http.fetch(url, opts, cb) or lemurx.async/await.
  4. If you need local capabilities (cookies, logged-in requests), document which bridge script the user must install, fetch it with lemurx.import("name"), and degrade gracefully when it is nil.
  5. No phishing-style full-screen with a hidden URL bar. Review rejects it.
  6. All outbound requests go through lemurx.http.fetch; list the domains in the file header comment.
  7. Provide a reset: on uninstall the script should theme.reset() + ui.unmount("*") + net.clearRules().
  8. Version in the first line: -- myskin v1.0.0.

lemurx.async · await · sleep

browserUGC ok

Coroutine sugar so waiting on the network never blocks the shared Lua thread.

lemurx.async(fn)
Run fn as a coroutine task. Errors inside are logged with a traceback, not swallowed.
lemurx.await(fn, ...) -> results
Inside async only. Calls fn(..., callback) — any function whose last parameter is a callback (http.fetch, timer.after, your own) — yields, and returns what the callback received. Raises when called outside async.

Inside async only. Yields for ms milliseconds.

    lemurx.ui.update("fx", { text = a.status .. "/" .. b.status })
end)

Classes · luakit

Object protocol & signals

luakitbrowserrenderer

Every luakit object (widget, download, timer, page, dom_element, …) follows the same protocol:

  • type(obj) returns the class name ("widget", "page", …). pairs works on the object's public properties.
  • Properties are read/written as fields; a successful write emits "property::<name>".
  • obj:add_signal(name, fn) · obj:emit_signal(name, ...) · obj:remove_signal(name, fn) · obj:remove_signals(name).
  • Handlers run in registration order as fn(obj, ...). The first handler returning a non-nil value stops propagation and that value is what emit_signal returns (luakit's LUA_MULTRET semantics) — this is how navigation-request returning false vetoes.
  • Classes have module-level signals too: widget.add_signal("create", fn(w)), luakit.add_signal(...).
  • After destroy only obj.is_alive may be read; anything else raises.
